# ເອກະສານສະຫຼຸບຂັ້ນຕອນການເຮັດວຽກ (System Flow) ແລະ ການຈັດການຂໍ້ມູນ (CRUD) ຂອງລະບົບ EDL E-Document

ເອກະສານສະບັບນີ້ອະທິບາຍກ່ຽວກັບໂຄງສ້າງ, ຂັ້ນຕອນການເຮັດວຽກ ແລະ ການຈັດການຂໍ້ມູນ (CRUD) ຂອງລະບົບ **EDL E-Document** (ລະບົບຄຸ້ມຄອງເອກະສານເອເລັກໂຕຣນິກ) ທີ່ພັດທະນາດ້ວຍ NestJS, Prisma ORM ແລະ PostgreSQL.

---

## 1. ພາບລວມ ແລະ ຂັ້ນຕອນການເຮັດວຽກຂອງລະບົບ (System Workflows)

ລະບົບ EDL E-Document ຖືກອອກແບບມາເພື່ອຄຸ້ມຄອງທັງ **ເອກະສານດິຈິຕອນ (Digital Attachments)** ແລະ **การກວດສອບສະຖານທີ່ຈັດເກັບເອກະສານຕົວຈິງ (Physical Storage Tracking)** ໂດຍມີຂັ້ນຕອນການເຮັດວຽກຫຼັກ 3 ພາກສ່ວນຄື:

### A. ຂັ້ນຕອນການກວດສອບສິດ ແລະ ຊິງຄ໌ຂໍ້ມູນພະນັກງານ (Authentication & HRM Sync Flow)
1. **ການຊິງຄ໌ຂໍ້ມູນຈາກ HRM:** ລະບົບມີລະບົບເຊື່ອມຕໍ່ກັບຖານຂໍ້ມູນ HRM ພາຍນອກ ໂດຍໃຊ້ລະຫັດພະນັກງານ (`empCode`) ເພື່ອດຶງຂໍ້ມູນສ່ວນຕົວ ແລະ ຂໍ້ມູນການສັງກັດເຊັ່ນ: ສາຂາ (`Branch`), ພະແນກ (`Department`), ຝ່າຍ (`Division`), ຫ້ອງການ (`Office`), ແລະ ໜ່ວຍງານ (`Unit`).
2. **ການເຂົ້າສູ່ລະບົບ (Authentication):** ລະບົບໃຊ້ລະຫັດຜ່ານທີ່ຖືກແຮຊ (Hashed) ດ້ວຍ bcrypt ແລະ ອອກ Token ຜ່ານ JWT Strategy ສໍາລັບການຢືນຢັນຕົວຕົນ.
3. **การກວດສອບບົດບາດ (Role-Based Access Control - RBAC):** ລະບົບແບ່ງຜູ້ໃຊ້ອອກເປັນ 5 ບົດບາດຫຼັກ:
   * **`SUPER_ADMIN`**: ຄຸ້ມຄອງລະບົບທັງໝົດ, ອະນຸມັດຜູ້ໃຊ້ໃໝ່ ແລະ ປ່ຽນແປງສິດ (Roles).
   * **`HQ_ADMIN`**: ຜູ້ດູແລລະບົບສ່ວນກາງ (ສຳນັກງານໃຫຍ່). ສາມາດຈັດການ ແລະ ເບິ່ງສາງ, ຕູ້, ຊັ້ນວາງ, ແຟ້ມເອກະສານ ແລະ ປະເພດເອກະສານທັງໝົດທົ່ວປະເທດ, ພ້ອມທັງສາມາດເບິ່ງ ແລະ ຄຸ້ມຄອງເອກະສານໄດ້ທຸກສາຂາ.
   * **`BRANCH_ADMIN`**: ຜູ້ດູແລລະບົບປະຈໍາສາຂາ. ສາມາດຈັດການສາງ, ຕູ້, ຊັ້ນວາງ, ແຟ້ມເອກະສານ ແລະ ຄຸ້ມຄອງເອກະສານສະເພາະພາຍໃນສາຂາ ຫຼື ຝ່າຍຂອງຕົນເອງ.
   * **`USER`**: ພະນັກງານທົ່ວໄປ. ສາມາດສ້າງເອກະສານ, ອັບໂຫລດໄຟລ໌ແນບ, ຄົ້ນຫາເອກະສານ ແລະ ເບິ່ງສະຖານທີ່ຈັດເກັບໄດ້.

---

### B. ໂຄງສ້າງການຈັດເກັບເອກະສານທາງກາຍະພາບ (Physical Storage Hierarchy Flow)
ເພື່ອຄວາມສະດວກໃນການຄົ້ນຫາເອກະສານຕົວຈິງ, ລະບົບໄດ້ຈັດລຽງໂຄງສ້າງການເກັບຮັກສາຕາມລໍາດັບດັ່ງນີ້:

```
[Branch] (ສາຂາ)
   └── [Warehouse] (ສາງເກັບເອກະສານ)
          └── [Locker] (ຕູ້ເກັບເອກະສານ)
                 └── [Shelf] (ຊັ້ນວາງເອກະສານ)
                        └── [Folder / Kono] (ແຟ້ມເອກະສານທີ່ມີ QR Code)
                               └── [Document] (ເອກະສານຕົວຈິງ)
```

* **Folder (ແຟ້ມ / ໂກໂນ):** ແຟ້ມເກັບເອກະສານຈະມີ QR Code ສະເພาະຕົວ ສໍາລັບການສະແກນເພື່ອລະບຸຕໍາແໜ່ງ.
* **Shelf (ຊັ້ນວາງ):** ຈະມີການກຳນົດຄວາມຈຸສູງສຸດ (`maxQty`) ເພື່ອບໍ່ໃຫ້ເກັບເອກະສານເກີນກຳນົດ.

---

### C. ຂັ້ນຕອນການນຳເອກະສານເຂົ້າລະບົບ (Document Archival Flow)
> **ໝາຍເຫດ:** ລະບົບບໍ່ມີຂັ້ນຕອນການອະນຸມັດ (Approve) ຫຼື ປະຕິເສດ (Reject) ເອກະສານ ເພາະເອກະສານທີ່ນຳເຂົ້າລະບົບຈະຕ້ອງເປັນເອກະສານທີ່ຖືກຕ້ອງ ແລະ ກວດສອບແລ້ວກ່ອນນຳເຂົ້າ.

1. **ກວດສອບເອກະສານຕົ້ນສະບັບ:** ຜູ້ໃຊ້ຈະຕ້ອງກວດສອບຄວາມຖືກຕ້ອງຂອງເອກະສານຕົ້ນສະບັບກ່ອນ ແລ້ວຈຶ່ງນຳເຂົ້າລະບົບ.
2. **ການສ້າງເອກະສານ:** ຜູ້ໃຊ້ (`USER` ຫຼື Admin) ສ້າງເອກະສານໂດຍການປ້ອນຂໍ້ມູນຫົວຂໍ້, ເລກທີເອກະສານ, ປະເພດເອກະສານ, ເລືອກແຟ້ມຈັດເກັບຕົວຈິງ (`Folder`) ແລະ ອັບໂຫລດໄຟລ໌ແນບ.
3. **ການບີບອັດ ແລະ ຈັດເກັບໄຟລ໌:** ໄຟລ໌ທີ່ອັບໂຫລດຈະຖືກກວດສອບ, ບີບອັດ (Compress) ເພື່ອປະຢັດພື້ນທີ່ ແລະ ບັນທຶກລົງໃນລະບົບຈັດເກັບ.
4. **ການບັນທຶກປະຫວັດ (Audit Log):** ລະບົບຈະບັນທຶກປະຫວັດການກະທຳ, ວັນເວລາ ແລະ ຜູ້ເຮັດທຸລະກຳລົງໃນຕາຕະລາງ `audit_logs` ໂດຍອັດຕະໂນມັດ.

## 2. ລາຍລະອຽດການຈັດການຂໍ້ມູນ (CRUD) ໃນແຕ່ລະໂມດູນ (Modules)

### 1. ໂມດູນເອກະສານ (Document Module)
ໂມດູນຫຼັກໃນການຈັດການເອກະສານດິຈິຕອນ ແລະ ເອກະສານຕົວຈິງ.
* **Create (ສ້າງ):** 
  * ຜູ້ໃຊ້ (`USER`, `HQ_ADMIN`, `BRANCH_ADMIN`) ສາມາດສ້າງເອກະສານໃໝ່.
  * ສາມາດແນບໄຟລ໌ເອກະສານໄດ້ພ້ອມກັນສູງສຸດ 10 ໄຟລ໌ ໂດຍລະບົບຈະທຳການບີບອັດ ແລະ ບັນທຶກໄຟລ໌ອັດຕະໂນມັດ.
* **Read (ອ່ານ/ຄົ້ນຫາ):**
  * ຄົ້ນຫາ ແລະ ດຶງຂໍ້ມູນເອກະສານທັງໝົດແບບແບ່ງໜ້າ (Pagination) ພ້ອມທັງສາມາດກັ່ນຕອງ (Filter) ຕາມປະເພດເອກະສານ, ວັນທີ, ຫົວຂໍ້, ແລະ ສາຂາ/ຝ່າຍ.
  * ດຶງຂໍ້ມູນລະອຽດຂອງເອກະສານແບບລາຍຕົວ (`GetById`).
  * ເປີດອ່ານ ຫຼື ດາວໂຫລດໄຟລ໌ແນບ (`GetAttachment`) ໂດຍລະບົບຈະມີການກວດສອບສິດ: ຜູ້ໃຊ້ທົ່ວໄປ (`USER`) ຈະເບິ່ງໄດ້ສະເພາະເອກະສານທີ່ຕົນເອງສ້າງເທົ່ານັ້ນ.
* **Update (ແກ້ໄຂ):**
  * ບໍ່ມີການອະນຸມັດ/ປະຕິເສດເອກະສານ ເພາະເອກະສານທີ່ນຳເຂົ້າລະບົບຈະຕ້ອງຖືກກວດສອບ ແລະ ຢືນຢັນວ່າຖືກຕ້ອງແລ້ວ. ການແກ້ໄຂຂໍ້ມູນ metadata ຂອງເອກະສານ (ຖ້າມີ) ຈະດຳເນີນການໂດຍ `BRANCH_ADMIN` ຫຼື `HQ_ADMIN`.
* **Delete (ລົບ):**
  * ບໍ່ອະນຸຍາດໃຫ້ລົບເອກະສານໂດຍກົງຈາກ API ເພື່ອປ້ອງກັນການສູນຫາຍຂອງຂໍ້ມູນ ແລະ ຄວາມປອດໄພ.

### 2. ໂມດູນແຟ້ມເອກະສານ (Folder / Kono Module)
ຄຸ້ມຄອງແຟ້ມເອກະສານທາງກາຍະພາບທີ່ວາງຢູ່ເທິງຊັ້ນວາງ.
* **Create (ສ້າງ):** ຜູ້ໃຊ້ລະດັບ `USER`, `BRANCH_ADMIN`, `HQ_ADMIN` ສາມາດສ້າງແຟ້ມເອກະສານໃໝ່ ໂດຍຕ້ອງລະບຸຊັ້ນວາງ (`ShelfId`) ແລະ ລະບົບຈະສ້າງ QR Code ໃຫ້.
* **Read (ອ່ານ):**
  * ເບິ່ງລາຍການແຟ້ມເອກະສານທັງໝົດ ພ້ອມທັງລະບຸເງື່ອນໄຂຄົ້ນຫາ ແລະ ແຍກຕາມສາຂາ/ຝ່າຍ.
  * ເບິ່ງລາຍການແຟ້ມເອກະສານທັງໝົດທີ່ຢູ່ເທິງຊັ້ນວາງໃດໜຶ່ງ (`getByShelf`).
* **Update (ແກ້ໄຂ):** `HQ_ADMIN` ແລະ `BRANCH_ADMIN` ສາມາດແກ້ໄຂຂໍ້ມູນແຟ້ມເອກະສານ (ຊື່, ສະຖານະ, ລະຫັດສະຖານທີ່ອ້າງອີງ).
* **Delete (ລົບ):** ສາມາດລົບແຟ້ມເອກະສານໄດ້ (ສະເພາະສິດ `HQ_ADMIN` ເທົ່ານັ້ນ).

---

### 3. ໂມດູນຊັ້ນວາງເອກະສານ (Shelf Module)
ຄຸ້ມຄອງຊັ້ນວາງເອກະສານພາຍໃນຕູ້ເກັບ.
* **Create (ສ້າງ):** `HQ_ADMIN` ແລະ `BRANCH_ADMIN` ສາມາດເພີ່ມຊັ້ນວາງໃໝ່ ໂດຍຕ້ອງລະບຸຕູ້ເກັບເອກະສານ (`LockerId`) ແລະ ກໍານົດຄວາມຈຸສູງສຸດ (`maxQty`).
* **Read (ອ່ານ):** 
  * ເບິ່ງລາຍການຊັ້ນວາງທັງໝົດ (ຮອງຮັບການກັ່ນຕອງຕາມ Locker, Warehouse, Branch, Division).
  * ເບິ່ງລາຍການຊັ້ນວາງທັງໝົດທີ່ສັງກັດໃນຕູ້ເກັບເອກະສານໃດໜຶ່ງ (`getByLocker`).
* **Update (ແກ້ໄຂ):** `HQ_ADMIN` ແລະ `BRANCH_ADMIN` ສາມາດແກ້ໄຂຂໍ້ມູນຊັ້ນວາງ ແລະ ສະຖານະການນຳໃຊ້ໄດ້.
* **Delete (ລົບ):** ສາມາດລົບຊັ້ນວາງໄດ້ (ສະເພາະສິດ `HQ_ADMIN` ເທົ່ານັ້ນ).

---

### 4. ໂມດູນຕູ້ເອກະສານ (Locker Module)
ຄຸ້ມຄອງຕູ້ຈັດເກັບເອກະສານພາຍໃນສາງ.
* **Create (ສ້າງ):** `HQ_ADMIN` ແລະ `BRANCH_ADMIN` ສາມາດສ້າງຕູ້ເກັບເອກະສານໃໝ່ພາຍໃນສາງ (`WarehouseId`).
* **Read (ອ່ານ):**
  * ເບິ່ງລາຍການຕູ້ເອກະສານທັງໝົດ (HQ ເຫັນທັງໝົດ, Branch ເຫັນສະເພາະສາຂາ ແລະ ຝ່າຍຂອງຕົນເອງ).
  * ດຶງຂໍ້ມູນຕູ້ເອກະສານທັງໝົດທີ່ຢູ່ໃນສາງໃດໜຶ່ງ (`getByWarehouse`).
* **Update (ແກ້ໄຂ):** ແກ້ໄຂຂໍ້ມູນຕູ້ເກັບເອກະສານ (ຊື່, ຄໍາອະທິບາຍ, ສະຖານະ).
* **Delete (ລົບ):** ສາມາດລົບຕູ້ເກັບເອກະສານໄດ້ (ສະເພາະສິດ `HQ_ADMIN` ເທົ່ານັ້ນ).

---

### 5. ໂມດູນສາງເອກະສານ (Warehouse Module)
ຄຸ້ມຄອງຫ້ອງ ຫຼື ສາງເກັບເອກະສານຫຼັກຂອງແຕ່ລະສາຂา.
* **Create (ສ້າງ):** `HQ_ADMIN` ສາມາດສ້າງສາງໄດ້ທຸກສາຂາ, ສ່ວນ `BRANCH_ADMIN` ສ້າງໄດ້ສະເພາະພາຍໃນສາຂາຂອງຕົນເອງ.
* **Read (ອ່ານ):**
  * ເບິ່ງລາຍການສາງທັງໝົດ ພ້ອມແຍກຕາມສາຂາ/ຝ່າຍ.
  * ດຶງຂໍ້ມູນ Dropdown ສາຂາທີ່ກ່ຽວຂ້ອງກັບສາງ.
  * ດຶງຂໍ້ມູນສາງທັງໝົດທີ່ຢູ່ພາຍໃຕ້ສາຂາໃດໜຶ່ງ (`getByBranch`).
* **Update (ແກ້ໄຂ):** ແກ້ໄຂຂໍ້ມູນສາງ (ຊື່, ລະຫັດສາງ, ທີ່ຢູ່, ສະຖານະ).
* **Delete (ລົບ):** ລົບສາງເອກະສານອອກຈາກລະບົບ (ສະເພາະສິດ `HQ_ADMIN` ເທົ່ານັ້ນ).

---

### 6. ໂມດູນປະເພດເອກະສານ (Document Type Module)
ຄຸ້ມຄອງໝວດໝູ່ ຫຼື ປະເພດຂອງເອກະສານ.
* **Create (ສ້າງ):** `HQ_ADMIN` ເທົ່ານັ້ນທີ່ສາມາດເພີ່ມປະເພດເອກະສານໃໝ່ໄດ້.
* **Read (ອ່ານ):** ຜູ້ໃຊ້ທຸກລະດັບສາມາດເບິ່ງລາຍການປະເພດເອກະສານທັງໝົດ, ຄົ້ນຫາຕາມຊື່, ຫຼື ດຶງຂໍ້ມູນຕາມ ID.
* **Update (ແກ້ໄຂ):** ແກ້ໄຂຊື່ ແລະ ລາຍລະອຽດຂອງປະເພດເອກະສານ (ສະເພາະສິດ `HQ_ADMIN`).
* **Delete (ລົບ):** ລົບປະເພດເອກະສານ (ສະເພາະສິດ `HQ_ADMIN` ແລະ ຕ້ອງບໍ່ມີເອກະສານໃດໆ ໃຊ້ປະເພດນີ້ຢູ່).

---

### 7. ໂມດູນຜູ້ໃຊ້ ແລະ ລະບົບຄວາມປອດໄພ (User & Auth Module)
ຄຸ້ມຄອງບັນຊີຜູ້ໃຊ້, ສິດການເຂົ້າເຖິງ ແລະ ການເຊື່ອມໂຍງຂໍ້ມູນພະນັກງານ.
* **Create (ສ້າງ/ລົງທະບຽນ):**
  * ລົງທະບຽນຜູ້ໃຊ້ໃໝ່ (`register`).
  * ຊິງຄ໌ຂໍ້ມູນພະນັກງານຈາກລະບົບ HRM ໂດຍໃຊ້ `empCode` ເພື່ອສ້າງບັນຊີຜູ້ໃຊ້ໃນລະບົບອັດຕະໂນມັດ.
* **Read (ອ່ານ):**
  * ເບິ່ງຂໍ້ມູນສ່ວນຕົວຂອງຜູ້ໃຊ້ທີ່ກໍາລັງເຂົ້າສູ່ລະບົບ (`getProfile`).
  * ເບິ່ງລາຍຊື່ຜູ້ໃຊ້ທັງໝົດໃນລະບົບ (ສະເພາະສິດ `SUPER_ADMIN`).
* **Update (ແກ້ໄຂ):**
  * ປ່ຽນແປງລະຫັດຜ່ານຂອງຕົນເອງ (`changePassword`).
  * ຣີເຊັດລະຫັດຜ່ານຂອງຜູ້ໃຊ້ອື່ນ (ສິດຂອງ `BRANCH_ADMIN`, `HQ_ADMIN` ຫຼື `SUPER_ADMIN`).
  * ອັບເດດສິດ/ບົດບາດຂອງຜູ້ໃຊ້ (Role) (ສະເພາະສິດ `SUPER_ADMIN`).
  * ອະນຸມັດເປີດນຳໃຊ້ບັນຊີຜູ້ໃຊ້ໃໝ່ (`ApproveUser`) (ສະເພາະສິດ `SUPER_ADMIN`).
* **Delete (ລົບ):** ບໍ່ມີຟັງຊັນລົບຜູ້ໃຊ້ ແຕ່ຈະໃຊ້ການປ່ຽນສະຖານະບັນຊີເປັນປິດການນຳໃຊ້ (Inactive) ແທນ.

### 8. ໂມດູນບັນທຶກປະຫວັດ (Audit Log Module)
* **Create (ສ້າງ):** ລະບົບຈະບັນທຶກປະຫວັດການເຄື່ອນໄຫວ (ເຊັ່ນ: ການສ້າງເອກະສານ, ການແກ້ໄຂ, ການເບິ່ງເອກະສານ) ໂດຍອັດຕະໂນມັດຜ່ານ Repository ພາຍໃນ.
* **Read / Update / Delete:** ບໍ່ມີ API ໃຫ້ເປີດເຜີຍເພື່ອແກ້ໄຂ ຫຼື ລົບປະຫວັດ ເພື່ອຮັກສາຄວາມຖືກຕ້ອງ ແລະ ຄວາມໂປ່ງໃສຂອງຂໍ້ມູນການກວດສອບ.
